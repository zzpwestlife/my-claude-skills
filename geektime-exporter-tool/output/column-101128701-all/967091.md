## 我的真实体验和看法

工程搭建这件事，在 AI Coding 之前我做过很多次。Spring Boot 多模块、Vue 脚手架、Docker 配置、启动脚本，这些东西我闭着眼睛都能搭。但以前搭一套完整的工程至少要半天，如果加上前端、设计系统、基础组件，一两天不算多。

这次用 Claude Code 搭 Hify，我计了一下时间，大概两个多小时，前后端全部就绪，包括 UI 设计。

但我想说的不只是 “快了多少”，而是快在哪里、慢在哪里，这比一个数字更有参考价值。

快在哪里：

模板性工作全程不需要思考。Maven 多模块的 pom 结构、MyBatis-Plus 的分页插件配置、logback-spring.xml 的环境区分、线程池的 ThreadPoolExecutor 写法，这些东西我脑子里有，但每次都要查参数、查语法。有了 Claude Code，这类工作几乎不占时间。你描述清楚要什么，它生成，你 review，done。

慢在哪里：

两类情况让我多花了时间。第一类是我描述不够清楚，Claude Code 给了一个 “看起来合理但其实不符合我意图” 的方案。比如我让它生成线程池配置，没有说明线程名前缀的重要性，它给的 threadFactory 是默认的，调了之后日志里全是 pool-1-thread-3，没法区分。这个问题不在 Claude Code，在我的指令。第二类是启动报错排查，Claude Code 给出的修复方案偶尔是错的，需要来回两三轮才解决。这个是模型本身的局限，接受就行，后面会越来越好。

最让我惊喜的：

UI 设计这块。我是典型的后端工程师，对前端审美没有信心。但按照上一讲的方法，把产品定位、用户群体、风格参考描述清楚，Claude Code 给出的设计系统我很满意。侧边栏的深色 + 渐变主色的科技感，比我自己乱试颜色好多了。这让我意识到，很多以前觉得 “需要特定技能才能做的事情”，现在只需要你能描述清楚你想要什么。

下面展开三个问题，是课程里大家比较关心的。

### 1. 任务拆解到什么粒度才合适？

08 讲提到了任务拆解的两个标准：生成量是否超出一次 review 的范围、步骤间是否有依赖关系。但实际操作时，很多人不确定该拆多细。

我的经验是：以 “一次能验证” 为单位。

什么叫一次能验证？就是每个子任务做完，你能跑一个命令或者访问一个接口，确认这个子任务是对的。

- Maven 骨架搭完 → mvn compile 能通过
- hify-common 搭完 → 没有编译错误
- 业务空壳搭完 → Spring Boot 能启动
- 健康检查接口加完 → curl localhost:8080/api/v1/health 返回 200

每个验收点都是一个 “锚”，确认到这里是对的，往后出问题也知道问题在锚点之后。

拆得太粗，生成量大、验收困难、问题难定位。拆得太细，频繁切换上下文、效率反而低。所以，以一次能验证为颗粒度，一般是合适的。

### 2. Claude Code 报错了，怎么处理最高效？

08 讲演示了 mvn clean install 报错后，让 Claude Code 修复的过程，有同学问为什么要多轮才解决。

原因在于：Claude Code 修复报错的方式是根据错误信息推断原因，有时候推断不准确，给的修复方案解决了表面问题，但没解决根本原因，导致出现新的报错。

高效处理的方式是：把完整的错误上下文给它，而不只是最后一行报错。

差的方式：

好的方式：

完整上下文 + 相关代码 + 明确问一个 “根本原因”，Claude Code 的修复准确率会高很多。如果两三轮还没解决，停下来自己看一眼错误信息，往往问题比你想象的简单 —— 可能只是一个 Bean 注入失败，或者一个依赖版本冲突。

### 3. 前端 UI 打磨，怎么说才能让 Claude Code 改到位？

11 讲说了 “UI 细节打磨才是真功夫”，但很多后端工程师卡在这里，看出来哪里不对，但说不清楚怎么改。

有一个通用句式很管用：

举几个例子：

- 表格和顶部标题区之间间距太大，改成 16px
- 操作列的删除按钮颜色用红色，但不要 danger 类型的背景，用 text 类型红色文字
- 侧边栏菜单项选中态太不明显，选中的菜单项左侧加一条 3px 的蓝色竖线
- 弹窗提交按钮在 loading 时要有转圈动画，不能让用户以为没反应

不需要知道 CSS 属性名，不需要知道 Element Plus 的组件 API，只需要描述 “在哪里、什么问题、我想要什么效果”，Claude Code 负责把你的描述翻译成代码。

## 总结

回顾这节实操课展示的五个场景，有几个核心动作值得你记住。

- 认知对齐先于执行。每个大任务开始前，先让 Claude Code 读一遍 CLAUDE.md，确认它理解了约束。这一步不做任何代码，只是对齐认知，但能帮你在执行阶段少走弯路。
- 报错信息要完整。启动失败、编译报错，把完整错误日志给它，而不只是最后一行报错。上下文越完整，它的修复准确率越高。两三轮还没解决，停下来自己看一眼，往往问题没你想的复杂。
- SDD 闭环是日常。GlobalExceptionHandler 里硬编码错误码这个问题，发现了、改了、同步更新 CLAUDE.md，这就是 SDD 闭环在日常开发里的样子。不是什么宏大的流程，就是每次 Claude Code 跑偏时随手堵住同类问题的口子。
- UI 打磨要敢说。看出来哪里不对，直接说：间距太大、颜色不对、弹窗太宽。Claude Code 负责把你的判断翻译成代码，你不需要会写 CSS，但你需要有判断力。每一轮打磨都在训练这个判断力。

到这里，工程搭建篇完整结束。你手上现在有：前后端都能跑的工程骨架、三档就绪的后端基础组件、有品牌感的前端界面、一套可复用的前端公共组件。从下一讲开始，正式进入业务功能开发，第一讲是模型提供商管理。
